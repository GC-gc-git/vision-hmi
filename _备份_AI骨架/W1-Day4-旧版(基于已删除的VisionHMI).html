1三处挂载到底是哪三处（很多人挂错）

先把这张表吃透。你作业本里写的是「三处挂载」，但没说清是哪三处、分别管谁、能不能救程序。

入口管哪类异常进程能不能活
① Application.ThreadException 只有 UI 线程（消息循环里）没被 catch 的异常 能 —— 吞掉，程序继续跑
② AppDomain.CurrentDomain.UnhandledException 所有线程（后台线程、线程池、第三方回调）的未捕获异常 不能 —— 事件跑完，进程立刻终止
③ TaskScheduler.UnobservedTaskException async/await 里没被 await 的 Task 抛的异常 能 —— 调 SetObserved() 就能保
第 ② 处最容易被误解，也最常被面试问：它只能「留遗言」，救不了程序。
你在 AppDomain.UnhandledException 处理器里写日志 —— 日志确实写下来了， 但程序还是会死。这是 .NET 的设计：后台线程崩溃，进程就该终止，不能让半个程序带着未初始化状态继续跑。
所以这一处的价值不是「让程序不崩」，是「崩之前把证据留下」。
而第 ① 处才是真正「让程序活着继续跑」的 —— 因为 UI 线程活着，界面还在响应。

为什么 ② 不能省（新手最常见的错）

只注册 ① 的话：

// 相机采集线程里没 try/catch → 异常直接逃出去
// → 不会触发 Application.ThreadException（那只管 UI 线程）
// → 进程直接死，日志里什么都没有
← 这就是「程序半夜崩了，日志是空的」的原因
记这个类比： ① 是「前台出事故」—— 前台有人，能拦住，程序继续营业。
② 是「后台出事故」—— 后台没人，只能记录事故报告，程序关门。
③ 是「异步任务出事故」—— 你连它什么时候出的事都不知道，所以要单独挂一个。

挂载位置：必须早于任何业务代码

注册顺序错了，注册了也没用。 Application.SetUnhandledExceptionMode(UnhandledExceptionMode.CatchException) 必须在 Application.Run(...) 之前调用 —— 因为这个模式开关决定了 WinForms 消息循环怎么对待异常， 消息循环一旦跑起来就定死了。
你现在的 Program.cs 里 GlobalException.Install() 在 Application.Run 前面，这个顺序是对的，保持住。
用我自己的话说：为什么第 ② 处（AppDomain）明明救不了程序，也必须挂？

2第 ① 处：UI 线程兜底（唯一能"救程序"的）

先看 VisionHMI 里已有的写法，然后你亲手敲一遍（不要复制粘贴 —— 你得能背出来）。

// GlobalException.Install() 里
// ① UI 线程的未捕获异常 —— WinForms 最常见的那种
Application.ThreadException += (s, e) => Handle(e.Exception);

// ② 强制所有异常都走上面的处理器，而不是直接崩
Application.SetUnhandledExceptionMode(
    UnhandledExceptionMode.CatchException);
为什么必须先调 SetUnhandledExceptionMode，光订阅事件不够？
WinForms 默认的异常处理模式是 Automatic —— 调试时弹「JIT 调试器」对话框，发布时直接崩。
CatchException 才是「把异常交给我的处理器，别弹窗别崩」。 这是一个开关 + 一个处理器，两步缺一不可。

Handle 里该做什么（顺序很重要）

顺序动作为什么
① 先写日志AppLogger.Error(...)最优先。如果写日志失败或者后面弹窗卡住，日志已经是唯一的证据了。先留证据，再做其他事。
② 再弹提示MessageBox.Show(...)给现场的人一句人话。但如果程序马上要死，这句可能来不及被看到 —— 所以它排在日志后面。
③ 提示框本身要包 trytry { MessageBox... } catch { }这是最容易被忽略的一层。如果界面线程已经出问题了，弹窗本身也可能抛异常 —— 那你的兜底代码自己炸了，等于什么都没做。
你现有骨架里第 ③ 点已经做对了（GlobalException.Handle 里弹窗包了 try/catch，还写了注释解释为什么）。
这一条也是单元 1 的结论：日志自己绝不能抛异常，否则会盖掉原始异常。 你在单元 1 就学到了，今天用上了。

3第 ② 处：后台线程兜底（留遗言）

这一处写起来最简单，但最容易写出假安全感。

// ② 其它线程（非 UI）的未捕获异常 —— 相机回调、通讯线程
AppDomain.CurrentDomain.UnhandledException += (s, e) =>
    Handle(e.ExceptionObject as Exception);
注意 e.ExceptionObject 这个细节。它的类型是 object，不是 Exception。
因为它有可能是从非托管代码（C++ DLL）穿过来的 COM 异常对象 —— 那玩意儿不是 .NET 的 Exception。
所以必须写 e.ExceptionObject as Exception（可能得到 null），不能直接强转，否则会自己再炸一次。

这一处有个"加时赛"的实用技巧

因为进程马上就要终止，你的日志必须已经落盘。而写文件是有耗时的。

// 进程正在终止，给日志一点落盘时间
AppDomain.CurrentDomain.UnhandledException += (s, e) =>
{
    Handle(e.ExceptionObject as Exception);
    Thread.Sleep(800);   // 等日志刷盘
};
为什么这行有用：你的日志是 File.AppendAllText（带 lock、写完立刻关文件）， 正常情况下已经落盘了，不需要等。但如果你以后改成用 StreamWriter 保持文件打开（性能更好）， 那这 800ms 就是「让缓冲区刷出去」的保险。
记这个思路就行：崩溃前的最后机会，时间很宝贵，能留多少证据留多少。
千万别在 ② 里做这些事：
❌ 弹 MessageBox（进程要死了，弹出来也是死的，而且可能卡住）
❌ 往数据库写东西（连接要时间，可能来不及）
❌ 试图 Environment.Exit(0)（多此一举，它本来就要终止）
② 这一处只做一件事：把证据写进日志。

4第 ③ 处：async/await 的坑（W2 单元 1 会天天遇到）

这一处你现在还用不上（你还没学 async/await），但我先讲，因为它是最容易漏的一处。

// ③ async/await 里没被 await 的 Task 抛出的异常
TaskScheduler.UnobservedTaskException += (s, e) =>
{
    Handle(e.Exception);
    e.SetObserved();   // 告诉运行时：我处理过了，别终止进程
};
为什么必须有 SetObserved()？
不调的话，运行时会在 GC 回收那个 Task 的时候（可能几分钟后！）触发异常升级策略，把进程干掉。
这就是「程序跑着跑着，莫名其妙自己没了」的经典原因 —— 而且日志里什么都没有，因为异常发生的时间和崩溃时间对不上。
但更根本的解法不是挂这个事件，是别写出那种代码。
错误写法：DoWorkAsync(); —— 不 await，异常沉到底，无声无息。
正确写法：await DoWorkAsync();，然后外层 try/catch。
第 ③ 处挂载是兜底，不是解决方案。W2 单元 1 会专门讲这个。

5验证：崩了到底有没有留下证据

验收标准：任何地方崩了，日志里都有堆栈。光装上不算，要真的崩一次。

实验设计（3 个按钮，测 3 条路径）

按钮怎么触发应该看到什么
崩在 UI 线程按钮事件里直接 throw new Exception("测试UI崩溃")，不 catch 日志有堆栈 + 弹了提示框 + 程序还活着，还能继续点别的按钮
崩在后台线程Task.Run(() => { throw ...; }) 或 new Thread(...)，不 catch 日志有堆栈 + 程序终止（这是正常的、预期的）
崩在 asyncSomeAsyncMethod(); 不 await，方法里 throw 日志有堆栈（可能要等 GC 回收才触发 → 加个 GC.Collect() 加速）
第 2 个实验会让你的程序直接关掉 —— 这是预期结果，不是出 bug 了。
但你要亲眼确认两件事：① 崩之前，日志文件里确实写进去了堆栈（这才是单元 4 的意义）；
② 关掉之后再打开程序，日志内容还在（说明它是追加写，不是覆盖写）。
顺手验证第 ② 点很值钱 —— 你日志文件如果被覆盖，现场排查就彻底没戏了。

6单元 4 的三个坑（面试素材）

坑为什么错该怎么做
以为 AppDomain 能救程序事件跑完进程照样终止，还以为是自己写错了去查业务逻辑记住分工：① 能救，② 只能留遗言，③ 能救
注册顺序错SetUnhandledExceptionMode 在 Application.Run 之后调 → 模式已定死，注册了也不生效全部注册放 Program.cs 最开头
兜底代码自己抛异常日志写失败 / 弹窗失败 → 原始异常被盖掉 → 什么都没留下日志和弹窗各自包 try，兜底里不做有风险的事
还有一个坑不在代码里，在观念里：以为全局兜底能代替 try/catch。
错。全局兜底是最后一道保险丝，不是常规手段。
原因很实在：① 走到全局兜底，说明程序状态已经不确定了（可能在半初始化、可能资源没释放）；
② 全局兜底没法做业务处理 —— 相机超时你要重试、掉线你要停机，这些都得在 catch 里按错误码分支（单元 3 学的）。
所以：能预期的失败 → try/catch + 错误码；没预料到的意外 → 全局兜底留证据。
