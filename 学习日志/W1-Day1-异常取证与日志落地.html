0为什么第一个任务是这个

你机构老师说过"报错要会自我根据系统提示判断原因"——这个能力是对的,但现在有一个缺口:系统提示本身没告诉你足够的信息。

你现在的代码是这样:

catch(NullReferenceException ex) { MessageBox.Show(ex.Message); }
catch(Exception ex)              { MessageBox.Show(ex.Message); }

语法完全正确,catch 顺序也对(具体在前、父类在后)。问题在 ex.Message。

🔍 关键事实：Message 和 StackTrace 是两样东西
属性内容对你的价值
ex.Message"未将对象引用设置到对象的实例"只知道类型,不知道位置。所有空引用都是这句话,毫无区分度
ex.StackTrace方法名 + 文件名 + 行号 + 调用链这就是现场证据。有它你 10 秒定位;没它你只能到处加断点猜
ex.InnerException内层异常异常套异常时（比如包装成业务异常），内层才是根因

现代码运行时你会看到:弹出来的那句话,和你要排查的那一行没有任何关系。

1单元 1 的三个步骤

今晚 21:30 后开始,约 2 小时。卡住了就来问我,别硬扛。

步骤 1先让现在的代码崩一次,亲眼看到"没证据"长什么样

你现在的代码已经能触发 NullReferenceException(string str = null; int len = str.Length;)。先跑一次,把弹窗内容抄下来。

然后临时改一处,让堆栈露出来,对比一下:

MessageBox.Show("出错了:" + ex.Message + Environment.NewLine + ex.StackTrace);

验收：你能指着屏幕上的一行字说出"哦,原来是我这行 str.Length 出的问题",而不是"我不知道哪错了"。

⚠️ 关键观察点:StackTrace 里会有"行号"和"文件名"。这是整个单元的核心,盯住它。

步骤 2把证据写进文件,而不是只在屏幕上飘一下

MessageBox 会被人点掉,StackTrace 也会滚出屏幕看不见。所以证据必须落到磁盘。

今天先不引日志框架（机构那份 Log4Net 教程有坑,单元 5 才碰）。今天只用 System.IO 写一行:

private static void WriteError(string whereText, Exception ex)
{
    string dir = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "logs");
    if (!Directory.Exists(dir)) Directory.CreateDirectory(dir);

    string file = Path.Combine(dir, "error" + DateTime.Now.ToString("yyyyMMdd") + ".txt");
    string text = "[{0}] {1}{2}堆栈:{3}{2}"
        + string.Format("{0:yyyy-MM-dd HH:mm:ss}", DateTime.Now), whereText,
           Environment.NewLine, ex.ToString();

    File.AppendAllText(file, text + Environment.NewLine, Encoding.UTF8);
}

为什么是 ex.ToString() 而不是 ex.Message + ex.StackTrace？因为 ToString() 一次性给你类型名 + Message + StackTrace + InnerException 全套,一个都不漏。手拼容易漏。这个习惯请记住,它是你后面所有日志代码的基础。

💡 三个 API 你会用到，值得认一下
  • AppDomain.CurrentDomain.BaseDirectory → exe 所在目录。用它比硬编码路径可靠,换台电脑也不会挂
  • Directory.Exists → 目录不存在就创建,否则 AppendAllText 会抛 DirectoryNotFoundException
  • File.AppendAllText → 追加写。指定 Encoding.UTF8 不然中文可能乱码

验收：触发三次不同类型的异常,去 bin\Debug\logs\ 目录找到 error20261024.txt,里面有 3 段记录,每段都有时间、原因、堆栈行号。

步骤 3区分"该 catch"和"不该 catch"

你现在的两个 catch 写得太"热情"了——什么都 catch,等于什么都没区分。真实的工程判断是:

异常类型处理方式为什么
NullReferenceException
IndexOutOfRangeException
FormatException		属于代码缺陷正常流程不该发生。记日志 + 弹窗明确告诉开发者哪一步错了,但不该静默吞掉
你自己抛的业务异常捕获 → 弹业务提示 → 不写堆栈比如"相机未连接"。这是预期情况,不是 bug,写一堆堆栈是噪音
你没预料到的让全局兜底接住（单元 4 做）你在按钮里 catch Exception 兜不住所有路径

今天只要求你做到一件事:把"代码缺陷类"和"预期失败类"在代码里分开注释出来。用注释标记即可,不用真写业务异常(那是单元 3 的事)。

// 【代码缺陷类】理论上不该发生,要留证据
catch(NullReferenceException ex) { ... }

// 【预期失败类】业务上会发生,只需友好提示,不用堆栈
// catch (DeviceNotConnectedException ex) { ... }

验收：你能在代码里指出哪一行是"缺陷"、哪一行是"预期",并说出为什么它们的处理方式不同。

📍 常见卡点预告（提前告诉你，省你时间）
  • "找不到 logs 文件夹" → 它在 bin\Debug\logs\,不在项目根目录。而且必须先运行一次才会被创建
  • "StackTrace 是空的" → 说明异常是你主动 throw 的,不是真的崩溃。主动抛的异常本来就没有"发生现场"
  • "DirectoryNotFoundException" → 忘了 Directory.CreateDirectory,或者路径拼错
  • "中文乱码" → File.AppendAllText 没指定 Encoding.UTF8
  • "为什么不用现成的 Log4Net?" → 因为单元 5 你要自己写一遍才知道框架在做什么。先造轮子,再用轮子,这是理解最快的方式
