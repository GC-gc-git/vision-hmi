1我实测出来的两个事实（比任何资料都有说服力）

我把机构的队列组件原样抄了一份，在 net48 下跑了两组压测。结果如下。

1.1 实验一：并发写，会不会丢行？

Parallel.For(0, 3000, i => Logger.Write($"第{i}条\n"));
Thread.Sleep(1500);   // 等后台线程写完
File.ReadAllLines("log.txt").Length

发起 3000 条耗时: 6 ms
实际落盘: 3000 条  →  一条不少
结论：机构的队列组件在并发上是正确的。3000 条一条不少。
这跟你在单元 2C 亲手踩过的那个坑不一样 —— 那个坑是多个线程同时写同一个文件， 这套设计是所有线程只往队列里塞，真正写文件的只有一个线程，所以根本没竞争。
这个设计思路本身是对的，值得学。它是「生产者-消费者」模式。

1.2 实验二：进程立刻退出，尾部日志会怎样？

Logger.Write("第1条\n");
Logger.Write("第2条\n");
Logger.Write("第3条\n");
// 不 Sleep，主线程直接结束

[实验1] 写了 3 条，现在主线程立刻结束
--- 落盘内容 ---
(log.txt 不存在)
--- 行数 --- 0
结论：3 条日志，一条都没落盘。
原因：写日志的线程是 IsBackground = true 的后台线程，主线程一结束， CLR 发现只剩后台线程就直接退出进程 —— 队列里还排着的日志全没了。
而且它有个 Thread.Sleep(100)：每轮固定等 100ms 才批量写。 也就是说每一条日志最坏要等 100ms 才落盘，程序在这 100ms 内退出就丢。
这是队列方案的固有代价，不是这份代码写得差。
「异步」和「不丢」这两件事，在物理上是冲突的 —— 数据在内存队列里，进程就没了。
工业界的解法是：退出前必须 Flush（把队列里的东西强制刷出去）。 Log4Net 有 LogManager.Shutdown()，NLog 有 LogManager.Shutdown()， Serilog 有 Log.CloseAndFlush() —— 三个库都强制要求你调它。
而且这只是解决「正常退出」。崩溃、断电、任务管理器强杀 —— 那就没救了，只能靠日志本身已经落盘的那部分。
用一句话说清楚：为什么机构的队列组件「并发不丢行」，但「退出时会丢」？（提示：想想谁在写文件）

⚠️ 第四行那个「溢出策略」是三个库差异最大、也最容易被忽略的地方。
NLog 的 AsyncWrapper：
  • overflowAction="Discard"（默认值！）→ 队列满了直接丢，调用方永不阻塞
  • overflowAction="Block" → 队列满了阻塞调用线程，不丢，但会卡住业务
  • overflowAction="Grow" → 无视上限一直扩容 → 生产环境禁用，会 OOM
陷阱：<targets async="true"> 是简写，等价于 Discard + queueLimit=10000。
官方原话：如果你写了很多消息（短时间内超过 10000 条），消息可能会丢，这是预期行为。 工业现场绝不能直接用 async="true" —— 一旦日志量加大（比如打开报文级 Trace）就静默丢日志。

⚠️ 这不是理论 —— 我今天实测出来了：把 queueLimit 调成 10、写 500 条， 落盘只有 10 条，490 条凭空消失，程序一声不吭。 第 4.6 步你会亲手再造一次这个事故，然后填进学习记录。
如果客户说「日志太多把硬盘塞满了，能不能现场调小点、不用重新发版」—— 手写版能做到吗？为什么？

3那我到底该用哪个？（这是单元 5 要你回答的问题）

先说结论 —— 正确答案不是「手写」也不是「NLog」，是分层组合。
你手写的日志类负责业务语义（错误码分层、出处标注、堆栈格式、给 UI 的回调）， NLog 负责写入机制（异步队列、溢出策略、配置热重载、按天滚动归档）。
为什么不能二选一：
  • 纯手写 → 现场想调日志级别，必须重编译重发版，客户不接受
  • 纯 NLog → 你的错误码体系、出处标注、UI 回调全没了，那是你项目的核心价值
所以「该不该上日志库」不是一个技术问题，是一个规模问题 —— 但「上了之后怎么分工」是技术问题。
⚠️ 顺带纠正我上一版卡里的一个说法：
我之前写「手写版零丢失，队列和异步都做不到」—— 这句话对「崩溃瞬间」成立，但对「正常退出」不成立。
实测事实：我自己的 NLog 用 Block 策略跑 3000 条，一条不少（队列满了会阻塞等待，不是丢弃）。 所以准确的说法是：
场景手写 lock 版NLog + Block
正常写日志一条不少一条不少（实测 3000/3000）
进程崩溃瞬间保住（已落盘）丢队列里未落盘的
正常退出保住需要 Flush()，不调就丢
结论：NLog 用对了配置（Block），不丢日志。真正的差别在「现场可调」和「不阻塞业务线程」。

⚠️ 有一条常见误解要澄清（很多对比文章写错了）：
「NLog 不支持结构化日志」—— 这是错的。
NLog 从 4.4/4.5 起就完整支持 message template 和 ${event-properties}， 官方首页明确写着「Full support for structured logging」。 NLog 的结构化是够用的，只是不如 Serilog 的 @ 解构丰富。 Serilog 那 200 多个 sink 大多是面向云原生的（Seq / Elasticsearch / Datadog）， 在离线工控机上 95% 用不到，反而是负担。
三条工控机特有的坑（社区实战文章反复强调的）：
  • 路径权限：上位机若以 Windows 服务身份运行，${basedir}/logs 可能没写权限 → 文件创建失败 → 日志全丢，而且没有任何提示。建议用 C://ProgramData//<产品名>//logs
  • 磁盘被撑爆：7×24 跑几个月，必须配 maxArchiveFiles 或按天滚动 + 保留 30–60 天
  • 生产环境禁止用 MessageBox 报异常：无人值守时弹窗没人点，进程挂一整夜，看门狗也不重启

4.1 建项目 + 装 NLog（10 分钟）

  1. 新建 WinForm 项目，命名 w1-day5-NLog，框架选 .NET Framework 4.8（跟你其他工程一致）
  2. VS 里右键项目 → 「管理 NuGet 程序包」 → 搜索 NLog → 装 5.4.0
  3. 装完确认两件事：
    ① 项目根目录出现了 packages.config 和 packages\NLog.5.4.0\ 文件夹
    ② bin\Debug\ 里出现了 NLog.dll
⚠️ 这里有个坑，我先替你踩了：
你现在的工程是老式 csproj。如果你手改 csproj 加 <PackageReference> ， dotnet build 会编译通过但 NLog.dll 不会进输出目录（我实测过）—— 运行时直接 FileNotFoundException。
所以必须用 VS 的 NuGet 包管理器右键安装，它会生成老式 packages.config + <HintPath> 引用， 这套机制对老式工程才有效。你的项目没有 packages.config，说明之前没用过 NuGet —— 这次是第一次，正好练一遍。

4.2 写 NLog.config（这是 NLog 的核心，全部靠它）

在项目里新建一个文件叫 NLog.config，内容照抄下面这段（我实测过这一份一字不改能跑）：

<?xml version="1.0" encoding="utf-8"?>
<nlog xmlns="http://www.nlog-project.org/schemas/NLog.xsd"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      autoReload="true">
  <targets>
    <target name="asyncFile" xsi:type="AsyncWrapper"
            queueLimit="10000" overflowAction="Block"
            batchSize="200" timeToSleepBetweenBatches="0">
      <target xsi:type="File"
              fileName="${basedir}/logs/${shortdate}.log"
              layout="${longdate}|${level:uppercase=true}|${message}"
              keepFileOpen="false"
              archiveAboveSize="10485760"
              maxArchiveFiles="7" />
    </target>
  </targets>
  <rules>
    <logger name="*" minlevel="Debug" writeTo="asyncFile" />
  </rules>
</nlog>
⚠️ 三个必须现在就知道的坑（我全踩过了）：
坑现象正确做法
① 文件必须放 exe 同级 放在项目根目录 → 日志一条都不出，程序也不报错（静默失效，最难查） 设 csproj 里 <None Include="NLog.config"><CopyToOutputDirectory>Always</CopyToOutputDirectory>
或在 VS 里右键该文件 → 属性 → 「复制到输出目录」= 始终
② 相对路径按「当前工作目录」解析 同一个 exe，VS 里启动和双击启动，日志落在两个不同地方 用 ${basedir}（= exe 所在目录）而不是相对路径
我实测确认：${basedir} 解析到 exe 目录，不会漂
③ 命名空间在 Wrappers 下 写 using NLog.Targets; 然后用 AsyncTargetWrapper → CS0246 编译错误 要 using NLog.Targets.Wrappers;
我自己第一次编译就栽在这
顺便解释配置文件里这几个块（学习记录那栏要填的就是这个）：
  • targets —— 日志往哪写。里面每个 <target> 是一个"写入器"
  • xsi:type="AsyncWrapper" —— 异步包装器。它自己不写文件，是套在 File 外面的中间层：负责排队、批量、决定队列满了怎么办
  • overflowAction="Block" —— 队列满了怎么办。Block=阻塞等待（不丢），Discard=直接丢（静默丢），Grow=无限扩容（会 OOM）
  • queueLimit="10000" —— 队列最多存多少条
  • batchSize="200" —— 后台线程一次批量写多少条
  • fileName="${basedir}/logs/${shortdate}.log" —— 按天分文件。${shortdate} = 2026-10-29 这种格式
  • layout —— 每行长什么样。${longdate}=时间，${level:uppercase=true}=级别大写，${message}=你写的消息
  • archiveAboveSize + maxArchiveFiles="7" —— 单个文件超 10MB 就归档，最多留 7 个（防止硬盘被撑爆）
  • rules —— 什么级别写到哪里。minlevel="Debug" 是最低级别，writeTo 指向上面某个 target 的名字
  • autoReload="true" —— 配置文件改了自动生效，不用重启程序 ← 下面 4.5 步专门验它

4.3 在代码里写日志（3 行）

在 Form1.cs 里加这几行，不需要任何配置代码（NLog 自动找 exe 同级的 NLog.config）：

using NLog;

private readonly Logger _log = LogManager.GetCurrentClassLogger();

// 写日志（级别名和你的枚举长得不一样，注意）
_log.Debug("调试信息");
_log.Info("程序启动完成");
_log.Warn("图像曝光接近上限");
_log.Error("相机采图超时");
⚠️ 一个会让你意外的地方：NLog 5 的 LogLevel 不是 enum，是 class。
我用反射查过：typeof(LogLevel).IsEnum == False。
但它依然可以直接用 > 比较（LogLevel.Warn > LogLevel.Info 是 true），也有静态字段 Trace/Debug/Info/Warn/Error/Fatal/Off。
对比你自己写的 enum LogLevel { Debug=0, Info=1, Error=2 } —— NLog 是 7 级（多了 Trace 和 Off），而且类型体系不一样。
但你手写那套的思路是对的：因为枚举数值递增，所以 level < MinLevel 能成立。NLog 里对应的是 rule.SetLoggingLevels(min,max)。
⚠️ 更隐蔽的一个坑：Logger 这个名字会被同名类遮蔽。
如果你的项目里已经有一个叫 Logger 的类（比如机构那份队列日志组件你复制进来了），那么 using NLog; 导入的 NLog.Logger 会被同命名空间里的类盖掉 —— C# 规则是同命名空间的类型优先级高于 using 导入。
症状：编译报 CS0029: 无法将类型"NLog.Logger"隐式转换为"你的命名空间.Logger"。
两种解法：① 声明成接口 private static readonly ILogger _log = ...（推荐，接口名不会被遮蔽，将来换日志库也不用改）；② 把你自己那个 Logger 类改名，或写全限定名 NLog.Logger。
我实测复现过这个报错，不是理论推测 —— 编译器原话就是 CS0029: 无法将类型"NLog.Logger"隐式转换为"xxx.Logger"。
⚠️ 第三个坑：log.Error("Error", msg) 会把消息丢掉。
NLog 的 Error 有两个重载：Error(string message) 和 Error(string message, params object[] args)。
第二个重载里，第一个参数是「格式模板」，后面的才是要填进模板的参数。你写 Error("Error", msg)，模板里没有 {0} 占位符，msg 就被直接丢弃了。
我实测的输出：log.Error("Error", "真正的消息") → 日志里写的是 ERROR|Error，消息没了。
正确写法：_log.Error(msg)，只传一个参数。
顺带：消息里带 {} 花括号是安全的（实测 {0} 和 { 不是占位符 } 都原样输出），所以 $"[{code}][{where}]{ex}" 这种拼法放心用。

4.4 第一个实验：五级过滤（5 分钟）

在窗体上放个 button，点一次写这五条：

_log.Info("I-信息");

然后去 bin\Debug\logs\ 看当天的 log 文件，确认五条都在，而且级别是大写的。

${level:uppercase=true} 让 Info 变成 INFO —— 和你单元 2 自己实现的那个 .ToUpper() 是同一个效果，但 NLog 在配置里就能做，不用改代码。

4.6 第三个实验：亲手制造一次静默丢日志（10 分钟）★最值钱

这次你要故意制造事故，亲眼看到 NLog 的默认配置有多危险。

  1. 把 NLog.config 里的 overflowAction="Block" 改成 "Discard"，queueLimit="10000" 改成 "10"，batchSize 改成 "1"，timeToSleepBetweenBatches 改成 "50"（故意让后台线程写得很慢，好让队列爆掉）
  2. 重启程序，在 button 里写 500 条：
    for (int i = 0; i < 500; i++) _log.Info($"第{i}条");
  3. 等 2 秒，看日志文件里实际有多少行
预期结果（我实测过）：写 500 条，落盘只有 10 条。
而且程序不报错、日志里没有任何提示 —— 490 条日志凭空消失。
这就是 Discard 的可怕之处：它静默丢。你不知道丢了，直到某天客户说「怎么少了段记录」。
而这正是官方文档里那句警告的实体： <targets async="true"> 是简写，等价于 Discard + queueLimit=10000。
工业现场绝对不能直接用这个简写。要显式写 AsyncWrapper + overflowAction="Block"。

⚠️ 但别把 NLog 当成万能药，两个必须知道的限制：

5机构的《支持并发的异步日志组件》—— 我该学它什么、警惕什么

这份文档在 C://Users//guicai//Desktop//C#new//3_高级//Thread//。它不是 Log4Net 教程，是机构教你手写一个队列日志组件。

5.1 它讲对了三件事（值得学）

  • ① 写日志线程不能用线程池。原话："由写日志线程会长时间处于阻塞（或运行等待）状态，所以它不适合使用线程池"
    线程池的线程是共享的，被一个写日志任务长期占住，等于把公共资源霸占了。文档这条判断是对的。
  • ② 用队列 + 单写线程，天然避免竞争。所有调用者只入队，真正写文件的只有一个线程 —— 这从根上消除了「多个线程同时写同一个文件」的问题。
  • ③ 用 ManualResetEvent 做信号，避免忙等待。主线程 WaitOne() 阻塞休眠，不占 CPU。

5.2 它有两个坑（你自己要补上）

问题文档里的样子应该怎么补
尾部日志会丢 没有 Flush 机制，进程一退队列里的全没了
实测：3 条 → 落盘 0 条		 加一个 Flush()：把队列里的任务同步执行完再退出。
并在 FormClosing / UnhandledException 里调用它
文档自己标了 todo lock (_queue) { ... } // todo: 这里存在线程安全问题，可能会发生阻塞。 这个 todo 说的是持锁期间入队可能阻塞调用方。
更好的做法是用 ConcurrentQueue（.NET 4.0+ 自带，无需第三方库）替代 Queue + lock
「学会它的思路 + 补上它的坑」—— 这个动作本身就是面试素材。
面试时你可以这样讲：
「我参考了机构的队列日志组件设计，自己判断出它缺 Flush 机制会丢尾部日志， 我实测验证了（3 条日志进程退出时落盘 0 条），然后用 ConcurrentQueue 换掉了它的 Queue + lock。」 这段话里有：读过资料、独立判断、动手实测、动手改进。四层都在。
