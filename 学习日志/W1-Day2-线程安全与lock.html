0开课前：5 分钟想清楚「多线程写日志」到底会出什么事

先别写代码。你现在的 AppLogger.Write 是这样工作的：

// 简化后
string file = Path.Combine(dir, prefix + DateTime.Now.ToString("yyyyMMdd") + ".txt");
File.AppendAllText(file, content, Encoding.UTF8);

File.AppendAllText 内部做了三件事：打开文件 → 定位到末尾 → 写入 → 关闭。

现在问自己一个问题：如果三个线程在「第 1 步和第 3 步之间」同时进来，会发生什么？

关键事实：文件打开时是独占的。第二个线程想在同一个文件上打开写，操作系统不会排队等它 —— 它直接抛 IOException（文件正被另一进程使用）。

而你的 Write 里有一个 catch，它会把异常吞掉，只往 Debug 窗口写一行。

于是结果是：程序不崩、日志文件正常生成，但你以为是 150 条，文件里可能只有 50 条，而且你完全不知道少了哪些。

用你自己的话说一遍：多线程写日志为什么会丢行？（不用抄上面那段）

1前置：把 MinLevel 改回 Debug，否则实验白跑

这一步不做，实验一定失败。你昨天为了验证级别开关，把 AppLogger.MinLevel 改成了 LogLevel.Error。 现在 LogInfo() 会被过滤掉，一条都写不进文件 —— 你会看到「150 条一条都没有」，然后误以为复现了丢行，其实是级别过滤。

改这一行：

// AppLogger.cs 第 27 行左右
public static LogLevel MinLevel = LogLevel.Debug;   // ← 改回 Debug

2第一次跑：故意不加锁，做一次 3 线程 × 50 条压测

在 Form1 里加一个按钮（或者直接在 Form1_Load 里跑），做这件事：

  • 开 3 个线程（用 Task.Run，机构教过）
  • 每个线程循环 50 次，调 AppLogger.LogInfo(...)
  • 每条消息里带上线程编号 + 序号，比如 T1-007 —— 这样你能看出哪一条丢了，而不只是「少了几条」
  • 跑完后数一下 info 文件里有多少行（VS 里用 Ctrl+F 搜 T 数，或者直接看行号）

同时做两件事

  1. 打开 VS 的「输出」窗口（Ctrl+Alt+O），盯着有没有红色的 IOException
  2. 记下实际行数
实验结果（实测，不是猜的）
很可能一次都不复现。File.AppendAllText 持锁的时间只有几条指令，150 次撞上的概率不高。
如果没复现，可以加大压力：5 个线程 × 200 条，或者在每次写之前加一点 Thread.Sleep(1) 把窗口拉长。
但请记住下面这句话，它比复现本身重要得多 ↓
「没复现」不等于「没问题」。
真实项目里的现象是：跑一天没事，跑三天丢几行，而且你不知道丢在哪。现场排查这种偶发丢行的成本极高。
所以：即使这次没复现，也必须加锁。这就是工程知识 —— 有些 bug 你复现不出来，但你知道它的成因，所以照样要防。
（面试时这句话的分量比「我复现出来了」更高）

3加 lock：让写入排队

现在给 AppLogger 加一把锁。加在类里，锁对象必须是一个固定的、唯一的对象：

public static class AppLogger
{
    // 锁对象：整个类共用这一个
    private static readonly object _logLock = new object();

    private static void Write(LogLevel level, string msg, string whereText, Exception ex)
    {
        try
        {
            if (level < MinLevel) return;

            // 关键：把「打开 → 写入 → 关闭」整段包住
            lock (_logLock)
            {
                string dir = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "logs");
                if (!Directory.Exists(dir)) Directory.CreateDirectory(dir);
                string file = Path.Combine(dir, prefix + DateTime.Now.ToString("yyyyMMdd") + ".txt");
                /* 拼 content 的代码放这里 */
                File.AppendAllText(file, content, Encoding.UTF8);
            }
        }
        catch (Exception ex2) { System.Diagnostics.Debug.WriteLine(ex2); }
    }
}
lock 锁的到底是什么？不是「锁住文件」，也不是「锁住这个方法」—— 它锁的就是你传进去的那个对象（这里是 _logLock）。
规则很简单：所有要互斥的代码，必须 lock 同一个对象。你 lock _logLock，我也 lock _logLock → 我们俩排队。
你 lock 一个新对象，我 lock 另一个 → 我们俩同时进去，等于没锁。

再跑一遍完全一样的压测（同线程数、同条数、同消息格式），然后数行数。

加锁后的实测结果
验收标准：加锁后行数必须正好等于 150，一条不少。
如果加锁后还是少，说明你 lock 的对象不是同一个，或者 lock 的范围没包住整个「打开→写入」过程。

4lock 的四个坑（面试高频，必须能答）

坑为什么错该怎么做
lock(this)把锁对象暴露给外部，别人 lock 你的窗体，你的线程永远等不到 → 死锁永远锁一个私有的对象
锁字符串常量"log" 在字符串常量池里是全程序共享的，可能锁到别人也在用的对象锁 new object() 出来的私有实例
锁对象不是 static每次 new 一个新对象 → 锁的是不同东西 → 等于没锁private static readonly object
lock 里做慢操作里面弹 MessageBox、发网络请求 → 持锁时间长，其他线程全在等lock 里只放必须互斥的那几行

还有一条常被问的：lock 只能锁同一个进程内的线程。如果是两个程序（两个 exe）同时写一个文件，lock 管不了 —— 那要用 FileShare 或系统级 Mutex。
