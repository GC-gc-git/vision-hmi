2核心：挂上 ThreadException，让 UI 线程崩了不闪退

这一节是今天的正事。做完后，你的程序崩了会弹一句友好提示 + 日志里有完整堆栈。

2.1 三个关键点（先看懂再写）

关键点说明
只管 UI 线程后台线程（Task.Run、new Thread）崩了它抓不到。这是下一节要验证的。
要在 Run 之前挂Application.ThreadException += ... 必须写在 Application.Run(...) 之前。写在后面不生效。
提示框要自己包 try处理器里如果弹窗失败（弹窗本身抛异常），会盖掉原始异常。这就是你单元 1 学的那条结论。

2.2 代码骨架

在 Program.cs 里，在 Application.Run 之前挂上：

Application.ThreadException += delegate(object sender, ThreadExceptionEventArgs e)
{
    // ① 先写日志 —— 顺序不能反
    AppLogger.LogError("未捕获异常", e.Exception);

    // ② 再弹提示 —— 而且要自己包 try
    try
    {
        MessageBox.Show("程序遇到未处理的错误，已记录日志，请联系技术人员。",
                        "出错了", MessageBoxButtons.OK, MessageBoxIcon.Error);
    }
    catch (Exception ex2)
    {
        // 弹窗自己都失败了，只能往控制台写，绝不能再抛
        System.Diagnostics.Debug.WriteLine(ex2);
    }
};
为什么顺序是「先日志、后弹窗」？
万一弹窗那步失败了（弹窗本身抛异常），这时日志已经写进去了 —— 证据还在。
反过来先弹窗，日志就丢了，程序里什么都不剩。
这条规则不只用在异常处理里，任何「写证据」的操作都应该是最后一步兜底。
三个枚举值你要知道意思（SetUnhandledExceptionMode）：
Automatic（默认）→ 异常走 ThreadException，除非 app.config 里另有设置
CatchException → 永远走 ThreadException，忽略 app.config
ThrowException → 永远不走 ThreadException，异常直接往外抛（=闪退）
你现在不用写这一行，默认 Automatic 就够用。但你要知道它存在 —— 因为有些老项目 app.config 里会写 ThrowException，那种项目里 ThreadException 就是死的。

3为什么需要「三处挂载」—— 后台线程崩了，UI 线程的处理器抓不到

这一节不写多少代码，目的是让你彻底理解一件事：全局兜底不是一劳永逸的。

3.1 做个实验（先看清楚 Task 的「吞异常」特性）

再拖一个 button2，里面起一个后台任务去崩溃：

private void button2_Click(object sender, EventArgs e)
{
    Task.Run(() =>
    {
        throw new Exception("后台线程崩了");   // 注意：这里没有 await
    });
}
点 button2 会发生什么？—— 什么都不会发生。
程序不闪退、不弹提示框、日志里一条记录都没有、程序照常能点其他按钮。
原因：Task 是个「异常保险箱」。Task.Run 里抛的异常不会逃出 Task， 它被 Task 存进 Task.Exception（包成一个 AggregateException）。 你不 await、也不去读 Task.Exception，这个异常就永远没人看见。
⚠️ 这里有个版本差异，是很多教程写错的地方：
.NET Framework 4.0：未观察的 Task 异常在 GC 回收时会让进程直接终止。
.NET Framework 4.5+（你的项目是 4.8）：改成默认不终止进程，只在 Task 被 GC 回收时 触发 TaskScheduler.UnobservedTaskException 事件，事件跑完异常就被丢掉。
你可以在 app.config 里 加 <ThrowUnobservedTaskExceptions enabled="true"/> 把 4.0 的旧行为改回来（微软官方文档里有这个开关）。
面试可能问：「为什么你的 Task 崩了程序没反应？」——答「因为 4.5 之后默认不终止进程， 而且异常要等 GC 回收 Task 才可能浮现，时机还不确定，所以不能靠它兜底」。
所以单元 4 的真正结论是这句：
「全局兜底不是一劳永逸的」 —— 挂了三处，也不代表所有异常都接得住。
Task 里的异常，谁都接不住；唯一的办法是 await 它（见 3.4）。

3.2 第二处：AppDomain.UnhandledException（只留遗言，救不回来）

再挂一处，它管除了 UI 线程以外、逃逸出来的未处理异常（裸后台线程、线程池线程）：

AppDomain.CurrentDomain.UnhandledException += delegate(object sender, UnhandledExceptionEventArgs e)
{
    // 这里只能做一件事：把证据留下来
    try
    {
        Exception ex = e.ExceptionObject as Exception;
        AppLogger.LogError("进程级未捕获异常", ex);
    }
    catch { }
};
关键：e.ExceptionObject 的类型是 object，不是 Exception。
必须 as Exception 转一下。它可能是 COM 异常穿过来的，强转会自己再炸一次。
用 (Exception)e.ExceptionObject 强转的话，遇到非 Exception 的对象直接 InvalidCastException，在「处理异常的地方」再抛异常 —— 这是最难受的一种崩。
这一处有个必须记住的限制（面试会问）：
AppDomain.UnhandledException 跑完，进程就终止了 —— 它救不了程序。
所以这里只能写日志，不能弹窗、不能写数据库、不能 Environment.Exit。
对比一下：ThreadException 里，程序能继续跑（能救）；AppDomain 这处，只能留证据（只能记录）。

3.3 第三处：TaskScheduler.UnobservedTaskException（先不动，但要知道它存在）

处理「Task 的异常没人 await」的漏网之鱼。你今天先不动它，理由：

  • 它只在 Task 被 GC 回收时才触发 —— 内存不紧张时可能几小时都不触发，甚至永远不触发
  • 微软官方文档明确说：不要用它替代正常的异常处理，它只是补漏
  • W2 开始搞异步采图之后，这条才会真正出现在你的代码里
  • 但你要知道它存在 —— 面试被问「异步里的异常怎么兜底」时，能说出这三个名字就够了

3.4 正确的做法：await 它（这才是工程上真正该写的代码）

再拖一个 button4，用 async + await + try/catch 来接住同一个异常：

private async void button4_Click(object sender, EventArgs e)
{
    try
    {
        await Task.Run(() => { throw new Exception("后台线程崩了"); });
    }
    catch (Exception ex)
    {
        AppLogger.LogError("Task里的异常（已接住）", ex);
        MessageBox.Show("接住了，程序没崩");
    }
}
预期现象：程序不闪退，弹出「接住了，程序没崩」，日志里有完整堆栈。
原因：await 会把 Task 里存的异常重新抛出来，抛在 await 所在的那个线程上。 你在 await 外面包了 try/catch，所以异常被你亲手接住了，压根走不到任何全局兜底。
为什么这是「唯一正确的姿势」？
因为它把异常交到了你手上，你才能做业务判断 —— 比如：
  • 相机超时 → 重试（产线继续跑）
  • 相机掉线 → 停机报警（再跑下去撞坏产品）
全局兜底只能「记一笔」，它没法帮你做这种分支。
这正是你单元 3 学的错误码的用处：catch 里面按码分支，全局兜底只是最后一道保险。
顺手记一条以后一定会踩的坑：async void 是黑洞。
async void 只能用在 UI 事件处理器上（比如这里的 button4_Click）。 其他任何地方用 async void，异常会直接打到 AppDomain → 进程必死。
微软官方 Premier Developer 博客专门讲过这个：async void 如果拿不到同步上下文（跑在线程池上）， 异常既不触发 UnobservedTaskException，也不触发 ThreadException，直接穿到 AppDomain。

AppDomain.CurrentDomain.UnhandledException裸线程（new Thread）、线程池线程

这张表就是你单元 4 的核心产出。
面试问「你的程序崩了会怎样」，最高分的答案是：
「UI 线程的异常我能在 ThreadException 里捕获，程序不会闪退；非 UI 线程崩了，我只能在 AppDomain.UnhandledException 里写日志 —— 这个事件跑完进程就终止了，救不回来。
