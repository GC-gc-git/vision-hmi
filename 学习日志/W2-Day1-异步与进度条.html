1先搞清楚：界面为什么会卡

WinForms 的界面是单线程的。所有控件的绘制、点击响应，都在 UI 线程（也叫主线程）上排队执行。

所以只要你在 UI 线程上干一件耗时的事 —— 比如读 5000 个文件、连一次 PLC、等相机一帧图像 —— 界面就冻住：按钮点不动，进度条不动，用户以为程序死了。

// ❌ 错误示范：耗时操作写在按钮事件里
private void button1_Click(object sender, EventArgs e)
{
    var data = Read5000Files();   // 5 秒
    listBox1.Items.Add(data);        // 用户在这 5 秒里什么都干不了
    progressBar1.Value = 100;         // 一次性跳到 100，中间没有过程
}

解法的思路只有一句话：耗时活挪到别的线程去干，界面线程只负责"接收结果并刷新"。

但「挪到别的线程」之后立刻冒出新问题：

  • 后台线程想改界面上的进度条 → 跨线程访问控件，直接抛异常
  • 任务中途用户想中止 → 没有取消机制，只能干等
  • 后台线程里出错了 → 异常被"吞掉"，界面毫无反应

今天这一个单元，就是把上面三个问题一次解决干净。所以你会同时学到 Task、IProgress、CancellationToken —— 它们是一套东西，不是三个孤立的 API。

2官方 API：我查到的结论（附出处）

2.1 IProgress<T> —— 进度回报的官方标准做法

微软官方文档对 Progress<T> 的描述里有一句关键的话：

「Any handler provided to the constructor or event handlers registered with the ProgressChanged event are invoked through a SynchronizationContext instance captured when the instance is constructed. If there is no current SynchronizationContext at the time of construction, the callbacks will be invoked on the ThreadPool.」
—— 微软官方文档 Progress<T> 类Remarks 章节（learn.microsoft.com/en-us/dotnet/api/system.progress-1）

翻译成人话，就三句：

  1. Progress<T> 在创建的时候把当前的线程上下文（UI 上下文）存下来
  2. 之后不管你在哪个线程调 Report()，回调都会自动切回创建它时的那个线程
  3. 如果在没有 UI 上下文的地方创建（比如线程池里 new），回调就退回到线程池跑 —— 这时候在里面改控件会炸

这意味着：你不需要手写 Invoke，进度回调自己会回 UI 线程。但代价是 Progress<T> 必须在 UI 线程上创建。

⚠️ 一个实测踩到的语言细节：Report 调不到。
我第一次写的时候直接 new Progress<int>(...).Report(i)，编译器直接报错：
error CS1061: “Progress<int>”未包含“Report”的定义
原因：Progress<T> 对 IProgress<T> 是显式接口实现（explicit interface implementation）。Report 这个方法名对外不可见，必须先转成接口类型才能调：
IProgress<int> progress = new Progress<int>(v => { ... });   // ✅ 声明成接口
progress.Report(i);                          // ✅ 这样才调得到

var progress = new Progress<int>(v => { ... });
progress.Report(i);                          // ❌ CS1061 编译不过
—— 我在 net48 下实际编译报错，修正后编译通过。官方文档 Progress<T> 页的 Explicit Interface Implementations 一栏也列着 IProgress<T>.Report(T)。

2.2 Task.Run —— 把 CPU 密集活挪出 UI 线程

微软官方文档的措辞是：

「For modern asynchronous programming, use async methods and await. If you need to explicitly offload processor-intensive work, use Task.Run to create and start the task, and you can then await that task as you would any other asynchronous operation.」
—— 微软官方文档「如何使用控件处理跨线程操作」(learn.microsoft.com/zh-cn/dotnet/desktop/winforms/controls/how-to-make-thread-safe-calls-to-windows-forms-controls?view=netframeworkdesktop-4.8)

2.3 async void —— 它的危险来自哪里

你 W1 的 Day4 已经做过 await + try/catch，那时候我说过「await 之后异常能在调用处捕获」。这句话对 async Task 成立，但对 async void 不成立。

微软官方开发者博客把机制讲得很清楚：

「The unhandled exception of the async void method is marshaled to a current synchronization context... In Windows Forms an unhandled exception in the event handler triggers Application.ThreadException event.」
—— 微软官方开发者博客《One user scenario to rule them all》(devblogs.microsoft.com/premier-developer/one-user-scenario-to-rule-them-all)

连起来读，逻辑就通了：

  • async Task 的异常被存进返回的 Task → 你 await 它，异常就在你的 try/catch 里
  • async void 没有 Task 可以存 → 异常直接丢给同步上下文 → WinForms 里就触发 Application.ThreadException
  • 好消息：你在 Day4 已经把 Application.ThreadException 接好了，所以不会闪退，但你会在日志里看到一条你没预期的异常
  • 坏消息：如果这个 async void 是在线程池上调用的（没有同步上下文），异常会变成进程级未捕获异常，程序直接终止
所以规则就一条：async void 只能写在事件处理器里，而且内部必须自己 try/catch。
其他所有地方一律 async Task。

2.4 CancellationToken —— 让用户能中止

取消不是「杀掉线程」，而是协作式的：你在循环里主动检查一个标志位，看到就自己停下来、抛出 OperationCanceledException。

这也意味着：取消信号必须传进到真正干活的那个方法里面，靠外层按钮去杀是杀不掉的。

测什么实测数据结论
1. Progress<T> 回调会回 UI 线程吗 UI 线程 ID = 1；回调所在线程集合 = [1]（5 次回调全在 UI 线程） ✅ 是 不用手写 Invoke
1b. .Wait() 会影响进度刷新吗 用 await → 收到 3/3 次回调

2. Task.Run 真的换线程了吗 工作线程 ID = 3，UI 线程 ID = 1 ✅ 是 UI 不会被占住
3a. async void 内部 try/catch 能抓到吗 抓到：boom-void ✅ 能
3b. async Task 在 await 处能抓到吗 抓到：boom-task ✅ 能
3c. async void 不 try/catch 会怎样 异常被抛到 SynchronizationContext，模拟的 UI 泵打印：[UI泵捕获] InvalidOperationException ⚠️ 走 ThreadException 真实 WinForms 就是 Day4 接的那个
4. 取消会抛什么 OperationCanceledException，已处理 10 轮后停下 ✅ 是 这是取消的正常信号，要单独 catch
5. 没有 UI 上下文时 Progress<T> 去哪 回调线程 ID = 4（不是 UI 线程 1）→ 退到线程池 ⚠️ 必须 UI 线程上 new
🔴 1b 这条数据是今天最重要的发现。
.Wait() 和 await 的区别，不是"风格问题"，是功能性的：
.Wait() 会同步阻塞 UI 线程 → 消息泵停转 → Progress<T> 的回调排在队列里没人处理 → 进度条永远停在 0。
await 会把 UI 线程还回去 → 消息泵继续转 → 回调被处理 → 进度条平滑刷新。
换句话说：你写的异步代码界面卡不卡，不取决于你有没有用 async/await，而取决于你有没有在 UI 线程上用 .Wait()。 这是面试官问「界面卡顿怎么解决」时，能答出深度的那一层。

4.2 第一步：把"干活"和"刷界面"分开

先想清楚职责划分，这是整个单元的核心思路：

  • 干活的方法：不认识任何控件，只管算、只管回报进度
  • 界面刷新：交给 Progress<T> 的回调去做

先把干活的方法写出来（注意它没有 Control 参数，也不碰任何控件）：

// 干活的方法：只依赖 IProgress，不认识任何控件
private async Task DoWorkAsync(IProgress<int> progress, CancellationToken token)
{
    const int total = 100;
    for (int i = 1; i <= total; i++)
    {
        // ① 干活（假装在算，每轮 50 毫秒）
        await Task.Delay(50, token);

        // ② 检查取消 —— 必须主动检查，否则取消不了
        token.ThrowIfCancellationRequested();

        // ③ 回报进度（调用方在哪个线程都行）
        progress?.Report(i);
    }
}

为什么 progress 用 ?. 判空？因为 TAP 规范要求带 IProgress 参数的方法必须允许传 null（微软官方文档「以任务为基础的非同步模式 (TAP)」明确写了这条）。

4.3 第二步：按钮事件里调用它

// 字段：取消令牌源
private CancellationTokenSource _cts;

private async void btnStart_Click(object sender, EventArgs e)
{
    try
    {
        // ① 每次开始都新建一个 CTS（不能复用！复用过期的会直接抛异常）
        _cts = new CancellationTokenSource();

        // ② Progress<T> 必须在 UI 线程上创建 —— 这一行就在 UI 线程，OK
        //    注意：声明成 IProgress<int>，不能写 var
        IProgress<int> progress = new Progress<int>(pct =>
        {
            // ③ 这个回调自动跑在 UI 线程，可以直接改控件
            progressBar1.Value = pct;
            lblStatus.Text = "处理中 " + pct + "%";
        });

        btnCancel.Enabled = true;
        lblStatus.Text = "开始处理...";

        // ④ await，不要用 .Wait()
        await DoWorkAsync(progress, _cts.Token);

        lblStatus.Text = "处理完成";
    }
    catch (OperationCanceledException)
    {
        // ⑤ 取消是正常流程，不是错误 —— 单独 catch，别弹错误框
        lblStatus.Text = "已取消";
    }
    catch (Exception ex)
    {
        // ⑥ 其他异常才是真错误
        //    这里接上你 Day1~Day5 写的 AppLogger
        lblStatus.Text = "出错了";
        AppLogger.LogError(ErrorCodes.Unknown, "异步任务异常", ex);
    }
    finally
    {
        btnCancel.Enabled = false;
        if (_cts != null) { _cts.Dispose(); _cts = null; }
    }
}

4.4 第三步：取消按钮

private void btnCancel_Click(object sender, EventArgs e)
{
    // Cancel() 只是"发信号"，不是"杀线程"
    // 真正停下来，靠 DoWorkAsync 里的 ThrowIfCancellationRequested()

6面试题对照（单元 1 学到这程度算够）

Q：「你的程序界面卡顿，你是怎么解决的？」
答到这三条就够：① 耗时操作（文件 IO、网络、相机取流、算法计算）用 Task.Run 挪到线程池，不占 UI 线程；② 进度回报用 IProgress<T>，它在创建时捕获 UI 的 SynchronizationContext，回调自动切回 UI 线程，不用手写 Invoke；③ 取消用 CancellationToken 协作式取消，OperationCanceledException 单独 catch，不当错误处理。
Q：「为什么不用 BackgroundWorker？」
这题现在成了你的加分项，因为大部分候选人只会说「因为教程都这么写」。你的答案：微软官方文档已明确标注 BackgroundWorker 不再是 WinForms 异步方案的推荐方法，它只解决"把处理器负载挪到另一个线程"，不处理文件 IO、网络这类真正会卡的操作，也没法组合多个异步任务。现代写法是 async/await + Task.Run + IProgress<T>。
Q：「Invoke 和 BeginInvoke 区别？」
Invoke 同步等待，UI 线程执行完才返回；BeginInvoke 异步投递，立刻返回。UI 更新常用 BeginInvoke（不阻塞）。
Q：「怎么知道要不要 Invoke？」
检查 InvokeRequired 属性（true 就说明当前不是 UI 线程）。标准写法：if (InvokeRequired) { BeginInvoke(...); return; }。但用 IProgress<T> 就不需要这层判断了。
Q：「async void 和 async Task 有什么区别？什么时候会出事？」
async Task 的异常存进 Task，await 时在调用处抛出，能被 try/catch 抓到；async void 没有 Task 兜底，异常直接抛给同步上下文，在 WinForms 里触发 Application.ThreadException；如果 async void 是在线程池上调用的（无同步上下文），异常会变成进程级未捕获异常，程序直接终止。所以：async void 只用在事件处理器里，且内部必须自己 try/catch。

8顺手修你自己的 bug（v4 里挂了很久的那个）

v4 计划第 4 节记着你的 Modbus 项目 E:\C#\C#-Modbus-Tcp\Form1.cs 有个必崩的 bug。我刚才确认了，它还在：

// 第 19 行
ModbusMaster master = null;
...
// 第 36 行
master = ModbusIpMaster.CreateIp(client);
...
// 第 43~44 行  ← 问题在这
master = null;        // ← 先置空了
master.Dispose();      // ← 再调用 → NullReferenceException

为什么必然崩：第 43 行把引用置成了 null，第 44 行再拿这个 null 去调 Dispose()，100% 抛 NullReferenceException。

📌 正确的释放顺序（单元 6 会正式讲，这里先看一眼）
顺序是反的：先 Dispose()，后置 null。而且 Dispose() 之前要先判空 —— 因为 CreateIp 可能本身就失败了。
为什么是「反向顺序」？因为依赖关系是反向的：被依赖的对象要先死，依赖它的才能死。master 依赖 client，所以 master 要先 Dispose，然后才是 client。这个原则你在单元 6 会完整用到（相机句柄、TCP 客户端、日志队列）。

这个改不改由你决定。但我建议今天顺手改掉 —— 它是你自己的代码，改了对简历有用（面试可以说"我 review 并修复了自己项目里的资源释放顺序 bug"）。
