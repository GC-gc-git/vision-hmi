1为什么光有英文异常不够

想象一下这个画面：

晚上 11 点，客户的产线停了。客户给你发一条微信：
[2026:10:27 23:41:02][button3]System.NullReferenceException: 未将对象引用设置到对象的实例。
客户看不懂，你也不知道是哪一行。这就是「只有英文异常」的全部信息量。

一个合格的错误信息要同时回答三个问题：

问题现在能回答吗工业项目里应该怎么答
哪一类问题能，但很笼统用错误码分段：E1xxx 设备类 / E2xxx 通讯类 / E3xxx 参数类
客户该怎么办完全不能错误码对应一条中文处置说明，客户照着做
程序怎么处理不能程序按错误码分支：超时→重试一次；掉线→报警停机
第三行是错误码真正的价值，也是最容易被忽略的价值。
很多同学以为错误码就是给客户看的「提示文字」。错。
错误的码 throw new BizException("E2001", "PLC通讯超时") 之后， 上层可以写 if (ex.Code == ErrorCodes.PlcTimeout) { 重试一次; } —— 用错误码驱动逻辑。 这才是工业上位机里错误码和普通提示信息的分水岭。
用你自己的话说：为什么「一句中文提示」不够，非要搞一个错误码？（不用抄上面）

2码段怎么分：一条规则定全局

分错码段，后面全乱。错误码一旦发给客户就不能随便改 —— 客户现场写死的报警逻辑会对不上。所以规则要在第一天定死。

规则一：按「模块」分，不按「严重程度」分

有人会想：「E1xxx = 严重错误，E2xxx = 警告」—— 这是错的。严重程度由日志级别（DEBUG/INFO/ERROR）表达，那是另一套东西，已经学过了。 错误码应该按功能模块分，这样客户报「E2003」时你立刻知道是通讯那块的问题。

规则二：前缀 + 4 位数字

E + 模块段 + 顺序号      // 模块段：哪一类问题；顺序号：这一类里的第几个

E1xxx  设备 / 采集类   // 相机、图像、光源
E2xxx  通讯类        // PLC、相机网口、Modbus
E3xxx  参数 / 流程类   // ROI 超界、模板没加载、流程配置错
E4xxx  业务 / 判定类   // 尺寸超差、NG、不良
E9xxx  兜底 / 未知     // 没 catch 住的意外，一律走这里
一定要留 E9xxx 兜底码。没有兜底码的工程，最后一条没被接住的异常就会裸奔到界面上， 客户看到 System.NullReferenceException —— 前面建的所有码段全部白建。

规则三：一个原因，永远只有一个码

「相机没连上」如果一会儿叫 E1001、一会儿叫 E3007，客户报障时你根本对不上。码表是字典，字典不能有同义词。

3写代码：一个带错误码的异常类

新建文件 BizException.cs。这是你今天的核心产出：

using System;

namespace w1_day2_线程安全
{
    // 业务异常：比普通 Exception 多带一个"业务错误码"
    public class BizException : Exception
    {
        // 错误码。放属性里，不要拼进 Message
        public string Code { get; private set; }

        public BizException(string code, string message) : base(message)
        {
            Code = code;
        }
    }
}
为什么 Code 要单独放一个属性，不能拼进 Message？
因为 Message 是给人读的（中文，可能改），Code 是给程序读的（契约，不能改）。
如果你写成 new BizException("E1002 相机采图超时")，那程序要判断就得做字符串切割 ex.Message.Substring(0,5) —— 一旦中文描述改了，程序就崩。这跟「用字符串解析代替结构化数据」是同一个错误。

再新建文件 ErrorCodes.cs，把码集中管理：

namespace w1_day2_线程安全
{
    // 错误码集中在这里。不要把 "E1001" 这种字符串散落到各个 .cs 文件里。
    public static class ErrorCodes
    {
        // E1xxx 设备 / 采集类
        public const string CameraNotConnected = "E1001";
        public const string CameraTimeout      = "E1002";

        // E2xxx 通讯类
        public const string PlcTimeout         = "E2001";
        public const string ModbusCrcError     = "E2002";

        // E3xxx 参数 / 流程类
        public const string RoiOutOfRange      = "E3001";

        // E9xxx 兜底
        public const string Unknown            = "E9001";
    }
}
为什么码要集中在一个类里，而不是直接写字符串？
写 "E1001" 散落在 5 个文件里 → 改一次要改 5 个地方，漏一个就出两种写法。
集中之后：改码 = 改一个地方；而且 IDE 能跳转、能拼写检查、能一眼看出全项目一共多少个码。

4让日志带上错误码

错误码写进界面还不够，必须写进日志 —— 否则事后翻日志还是只看到英文异常。

你现在的 AppLogger.LogError(string whereText, Exception ex) 签名里没有码的位置。最小改法：加一个重载，不动原来的方法（原来那个还要给「不带码的意外异常」用）。

// AppLogger.cs 里，在原有 LogError 旁边加一个重载
public static void LogError(string code, string whereText, Exception ex)
{
    Write(LogLevel.Error, code, whereText, ex);
}

然后 Write 的 Error 分支要把 msg（也就是码）也打进去。改一行：

// 你现在（码丢了，日志里只有 where 和堆栈）
File.AppendAllText(file, $"[{time}][{level.ToString()}][{whereText}]{ex}\n", Encoding.UTF8);

// 改成（把 msg 也就是错误码打进去）
File.AppendAllText(file, $"[{time}][{level.ToString()}][{msg}][{whereText}]{ex}\n", Encoding.UTF8);
改完之后的日志行长这样：
[2026-10-27 21:58:33-120][Error][E1002][相机采图]System.TimeoutException: 采集超时...
五个字段各司其职：时间 / 级别 / 错误码 / 出处 / 堆栈。
顺手把 level.ToString() 改成 level.ToString().ToUpper()。
你现在的标签是 [Info]、[Error]（首字母大写），日志里三个级别大小写不统一看着别扭， 而且跟工业现场常见的 [INFO] / [ERROR] 写法不一致 —— 客户 grep 关键字的时候大小写敏感就搜不到了。
三处都要改：Debug 分支、Info 分支、Error 分支。

5三层消费：抛出 → 记录 → 提示

同一个错误码，要在三个地方各出现一次才算做完整：

层干什么写在哪
抛出层业务代码发现异常，抛 BizException，带上码相机采图、PLC 读写那几行
记录层catch 住，LogError(ex.Code, ...) 写进日志界面层 / 全局兜底
提示层给用户一句能照着做的中文MessageBox

写法

// ① 抛出层：业务代码里抛
try
{
    if (!cameraConnected)
    {
        throw new BizException(ErrorCodes.CameraNotConnected,
                        "相机未连接，请检查网线和相机 IP");
    }
    image = camera.Capture();
}
catch (BizException ex)
{
    // ② 记录层：日志里必须带码
    AppLogger.LogError(ex.Code, "相机采图", ex);

    // ③ 提示层：给客户能照着做的一句话
    MessageBox.Show($"[{ex.Code}] {ex.Message}", "出错了");
    return;
}

然后加一层：按码分支

这一步是单元 3 的分水岭。做完上面那三步，你只是「把异常信息换成了中文」。加上按码分支，程序才真的「懂」了自己的错误：

catch (BizException ex)
{
    AppLogger.LogError(ex.Code, "相机采图", ex);

    // 按错误码决定程序怎么走 —— 这才是错误码的真正用途
    if (ex.Code == ErrorCodes.CameraTimeout)
    {
        // 超时是偶发的 → 重试一次，不打断产线
        MessageBox.Show("[E1002] 相机采图超时，正在重试...");
        return;
    }
    if (ex.Code == ErrorCodes.CameraNotConnected)
    {
        // 掉线是硬故障 → 报警停机，等人来处理
        MessageBox.Show("[E1001] 相机未连接，请检查网线或相机电源");
        plc.Stop();   // 停机
        return;
    }

    // 其余未预料到的业务错误，统一按兜底处理
    MessageBox.Show($"[{ex.Code}] {ex.Message}");
}
「超时重试」和「掉线停机」的区别，就是工业上位机和玩具程序的区别。
同一个「相机出问题」，超时就重试（产线继续跑），掉线就停机报警（再跑下去会撞坏产品）。
这个判断只有靠错误码才能写出来 —— 中文提示文字没法用来做分支。
catch 的顺序不能反！C# 从上往下匹配，第一个匹配上的就停。
如果你写 catch (Exception ex) 在前、catch (BizException ex) 在后 → BizException 那个分支永远进不去，而且编译器不报错。
正确顺序：catch (BizException) 在前，catch (Exception) 在后。

最后补一个兜底 catch，这是 E9xxx 存在的意义：

catch (Exception ex)
{
    // 没被接住的意外，一律给兜底码 + 写完整堆栈
    AppLogger.LogError(ErrorCodes.Unknown, "未预期异常", ex);
    MessageBox.Show("[E9001] 系统未知错误，已记录日志，请联系技术人员",
                    "出错了");
}

7单元 3 的三个坑

坑为什么错该怎么做
码拼进 Message要靠字符串切割才能判断，描述一改程序就崩码单独放 Code 属性
码散落在各个文件里改一次改 N 个地方，漏一个就出两种写法全部集中到 ErrorCodes
catch 顺序反了catch(Exception) 在前 → BizException 分支永远进不去，编译器不报错具体的在前，笼统的在后
还有一个坑不是代码坑，是「习惯坑」：错误码一旦发给客户就不能随便改。
所以要留一份码表文档（Excel 或 Markdown 都行），记着：码 / 含义 / 什么时候出 / 处置方法 / 日期。
